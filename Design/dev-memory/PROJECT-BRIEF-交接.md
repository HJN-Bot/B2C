## 1. 设计想法和思考

### 1.1 核心洞察 / 定位
**SpeakPeak = 中学生（6–9 年级）的英文演讲/辩论「私人陪练教练」，不是评分器、不是比赛、不是评价工具。**

背后的判断：孩子开口说英语最大的敌人是**怕被评判而不敢说**。市面工具大多在「打分/纠错」，
越纠越不敢开口。我们反着来——**先让他敢说、持续说，再在结束后给他能立刻用上的升级**。
所以产品的第一性目标不是"测出他多差"，而是"让他多说一点、下次说得漂亮一点"。

### 1.2 目标用户（窄切口）
不是"所有想学英语的人"，而是**有明确演讲/辩论场景的中学生**：周末辩论赛、科普演讲、
考试口语。切口窄，是为了让"练完就能用在那个真实场合"这件事成立——这是留存与付费的支点。

### 1.3 核心闭环（四个页面就是四步）
1. **Home 开始** —— 选场景（辩论/科普/考试/自由说，各有自己的话题库和教练风格）→ 给一个能直接开口的话题 → **一个大按钮开练**（不让他在设置里纠结）。
2. **Practice 练习房** —— 实时字幕 + 猫猫教练 + KTV 四维（Flow/Words/Sentences/Story）。关键设计：**说话过程中界面只放"帮他继续说下去"的东西**（比如卡住时弹"接下来可以说什么"），把分数/纠错全部挪到结束后，避免说话时被打断、被评判。
3. **Takeaway 复盘** —— 这是我们的**差异化主张**。不止给反馈，而是**"教你说漂亮"**：先肯定你最好的一句 → Level up 三件套（换更强的词 / 把你自己那句话改写升级 / storytelling 展开结构）→ Coach 追问。
4. **My 我的** —— 成长地图、词汇库、金句库、设置。

### 1.4 贯穿的设计原则
- **说话时"扶"，结束后"教"**：过程零评判，评价作为私有证据放到复盘。
- **学 → 复用闭环**：复盘里 pin 的金句 / 存的词，会在**下次练习的 Ready 卡**里带回来（"lines to try"），复盘的 one_move 会变成首页的"下次尝试点"。让每次练习不是孤立的。
- **场景化**：每个场景独立话题库 + 教练风格，练完能迁移到真实场合。
- **猫猫教练**：情绪陪伴，降低压力，把"练英语"变得没那么可怕。
- **i18n 边界**：界面可以切中文（降低使用门槛），但**练习内容始终英文**——因为它是英文教练，话题/AI 反馈/金句都得是英文。

### 1.5 战略与工程取舍
- **押场景 A**（有准备的演讲/辩论），走 upside 阶梯：**小闭环 → 第一个付费用户 → 清晰市场**。
- **分销走 IP 化，不做冷启动地推**：用 Owner 自己的**小红书账号**做内容推广 + 在**现有群**里拉群试用收反馈
  （借已有信任关系）。这决定了：**验证阶段几乎不依赖国内基建**，一个 Vercel 链接丢进群就能拿信号。
- **克制基建**：先用免费/借来的后端把闭环跑通，**冻结**自建 Supabase / ICP 备案投入 / 小程序，
  直到拿到 **1 个付费信号**再加码。理由：验证阶段最贵的是时间，不是把架构搞漂亮。
- **明确不上 LangGraph/LangChain**：纯前端 SPA 无服务端跑 agent 图，且与"冻结后端"冲突；
  "AI 反馈笼统"是 prompt/上下文问题，靠一句 prompt 让 AI 生成针对性内容即可解决，不需要框架。

## 3. Owner 的 concern（已与 Owner 确认，2026-07-26）

这些**不是并列清单，而是有根因层级**的。接手 agent 一定要理解这个结构，别把下游当优先级。

### 3.1 根本结点（最扎心）：不确定能不能推广出去 → 要不要继续投入
- Owner 对**分销/推广**没底：**靠自己花时间去找用户不可靠**。这才是"这个项目要不要继续投入"的真正结点。
- **"后端依赖别人不可控""国内访问没解决"都是这个根因的下游** —— 在"能不能推得动"验证出来之前，
  Owner 不想重投基建（备案 / 自建后端）。所以这两条**现在不是优先级，别急着修**。

### 3.2 Owner 的破局打法：IP 化，不做冷启动地推
- 用**自己的小红书账号**做内容推广（个人 IP 驱动）。
- 在**现有的群**里拉群、收集反馈（借已有信任关系，而不是陌生地推）。
- 关键含义：验证"能不能推广"这件事**几乎不需要国内基建** —— 小红书导流 + 群内试用就能拿第一波信号。
  这正是 3.1 说基建可以缓的原因。

### 3.3 确认要解决的产品问题（直接决定"值不值得推"）
1. **AI 反馈太笼统、不真实 —— 不行，必须修。** 产品得先真的好，才配拿去推。
   （正在做的 Takeaway 4 项修复就是冲这个去的。）
2. **成本 / API 选型要换 —— 确定要换一个 API 接口**（DeepSeek，OpenAI 兼容，国内更稳更省）。

### 3.4 需继续想清楚
- **"能不能跑出付费信号 / 市场是否清晰"是最根本的** —— 3.1 就是它的具体形态。
- **个人精力 / 投入产出比**要认真补：这是一个 **go / no-go 的决定，不是纯技术问题**。
  竞品密度（同名 SpeakSpark 已存在，说明赛道有人）也归在这条。

### 3.5 由此给接手 agent 的排序建议
在 Owner 做"继续 / 暂停"决定之前，最省的验证路径：
1. **先把产品做到值得推**：修 AI 反馈质量（Takeaway 4 项）+ 换 API（DeepSeek）。
2. **走 IP 化拿信号**：配合 Owner 小红书 + 现有群，把可分享链接（先用 Vercel，够用）丢进群试用。
3. **读到信号再谈基建**：有人真的愿意用 / 愿意付，才谈 .cn 备案 / 自建后端。**在此之前不碰重基建。**
